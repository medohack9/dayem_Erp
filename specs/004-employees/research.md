# Research: Employee Management

**Date**: 2026-04-25
**Feature**: 004-employees

## R-001: Employee table vs extending users table

**Decision**: Extend the existing `users` table with employee-specific columns

**Rationale**: The `users` table already has `department_id`, `status`, `deleted_at` columns from previous migrations. Since employees are users with role="employee", a separate table would create a 1:1 join that adds complexity without benefit. Adding columns directly keeps queries simple and consistent with how the auth system already works.

**Alternatives considered**:
- Separate `employees` table with FK to `users`: Would require joins on every query, complicate auth status checks, and add drift between user and employee records
- Polymorphic user types: Over-engineering for a single company internal system

## R-002: Employee code generation strategy

**Decision**: Sequential format `EMP-NNN` (e.g., EMP-001, EMP-002) generated server-side on create

**Rationale**: Simple, predictable, easy to sort. The code is generated by finding the current max code number and incrementing. No gaps from deleted employees (codes are never reused).

**Alternatives considered**:
- UUID-based codes: Hard to read, not human-friendly for an HR system
- Auto-increment ID as code: Too short, could leak information about total employee count
- Timestamp-based codes: Not sequential, hard to reference verbally

## R-003: Employee status transitions

**Decision**: Three statuses (active, suspended, terminated) with allowed transitions:
- active → suspended (admin action)
- active → terminated (admin action)
- suspended → active (admin reactivation)
- suspended → terminated (admin action)
- terminated → active (admin reactivation, rare but possible)
- No other transitions allowed

**Rationale**: Matches the existing `status` ENUM('active', 'suspended', 'terminated') in the users table. Suspended employees can't log in. Terminated = employment ended. Both can be reactivated.

**Alternatives considered**:
- Two-status (active/inactive): Too coarse for HR needs
- Five+ statuses (probation, on-leave, etc.): Over-scoped for current requirements

## R-004: Search and filter implementation

**Decision**: Server-side filtering with AJAX pagination, matching the departments module pattern

**Rationale**: Consistent with existing UX. Server-side avoids loading all records client-side. AJAX prevents full page reloads. The search bar and filter dropdowns submit via query parameters to the same endpoint.

**Alternatives considered**:
- Client-side filtering with full dataset: Won't scale past 500 employees, loads all data upfront
- Separate API endpoint for search: Adds unnecessary complexity; the list endpoint with params is cleaner
- DataTables/JS library: Constitution forbids external JS libraries

## R-005: Default password for new employees

**Decision**: New employees are created without login credentials. An admin can set/reset their password separately. The password field is required but defaults to a system-generated temporary password that the employee must change on first login.

**Rationale**: In an HR context, admins add employees who may not need system access immediately. However, the users table requires a password column with NOT NULL constraint. We'll generate a random temporary password using `password_hash()` and store it. When the employee needs access, the admin or employee can trigger a password reset.

**Alternatives considered**:
- Leave password NULL: Schema has NOT NULL constraint, would require ALTER
- Email-based invitation: Constitution specifies Arabic-only internal system, no email integration
- Use phone number as initial password: Security risk

## R-006: Department default salary suggestion mechanism

**Decision**: AJAX call to `/api/departments/active` (already exists) + `/api/departments/{id}/default-salary` (new endpoint) that returns the department's default_salary field. JavaScript populates the salary field on department change.

**Rationale**: Reuses existing department API. Lightweight endpoint. Admin can override the suggested value.

**Alternatives considered**:
- Embed all department salaries in the page HTML: Data exposure, doesn't scale
- Separate salary configuration module: Over-scoped for this feature

## R-007: Preventing admin self-deletion

**Decision**: Server-side check in delete handler: if the user ID being deleted equals the current session user ID, return 403 with Arabic error message

**Rationale**: Simple, reliable, cannot be bypassed client-side. Consistent with how RBAC is already enforced.

**Alternatives considered**:
- Hide delete button for own row (JS only): Can be bypassed
- Separate "account settings" flow: Over-scoped

## R-008: Employee code uniqueness and gap handling

**Decision**: On create, find max numeric suffix from existing codes using `SELECT MAX(CAST(SUBSTRING(employee_code, 5) AS UNSIGNED)) FROM users WHERE employee_code IS NOT NULL`, then increment. If no codes exist, start at 1. Soft-deleted employees retain their codes (no reuse).

**Rationale**: Simple MAX+1 approach. Codes are never reused even after deletion, which is standard HR practice (employee numbers don't get reassigned).

**Alternatives considered**:
- Separate sequence table: Over-engineering
- UUID codes: Not human-friendly
- Gap-filling (reuse deleted codes): Confusing for HR records, can cause legal issues

## R-009: Auth system integration for suspended/terminated employees

**Decision**: Modify `AuthController::login()` to check `status = 'active'` before allowing login. If status is suspended or terminated, show Arabic messages: suspended → "حسابك موقوف. تواصل مع الإدارة.", terminated → "حسابك منتهي. تواصل مع الإدارة."

**Rationale**: Minimal change to existing auth flow. The `UserModel::findByIdentifier()` already excludes deleted_at users. We add a status check after successful credential validation but before session creation.

**Alternatives considered**:
- Middleware check on every request: Unnecessary overhead since status can't change mid-request
- Separate "account status" module: Over-scoped
