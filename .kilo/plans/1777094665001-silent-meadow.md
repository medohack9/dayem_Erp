### 1.2 Request/Response Issues

**Issue #1: Salary Validation Bug in Update (EmployeeController.php:315)**
```php
if (empty($salary) && $salary !== '0' && $salary !== 0 && $salary !== $employee['salary']) {
    $errors['salary'] = 'المرتب مطلوب';
}
```
- **Problem**: The condition logic is incorrect. It checks `$salary !== $employee['salary']` which means if salary is unchanged, validation passes even if empty. Should only validate if salary is being changed.
- **Impact**: Can't properly validate salary on update when it's empty.

**Issue #2: Unused Temp Password (EmployeeController.php:179)**
```php
$tempPassword = $this->employeeModel->generateTempPassword();
```
- **Problem**: `$tempPassword` is generated but never used. The password comes from form input instead.
- **Impact**: Confusing code, possible design inconsistency with spec.

**Issue #3: Profile Photo Upload Discrepancy**
- **Spec says** (spec.md:137): "Profile photo upload is out of scope for this phase"
- **Implementation has**: Full profile photo upload in employees.js (lines 197-230) and edit.php
- **Impact**: Scope creep - feature implemented that spec explicitly excluded

## 3. Database & Migration Issues

**Issue #4: Hardcoded Database Name (004_employees.sql:4)**
```sql
USE dayem_erp;
```
- **Problem**: Hardcodes database name, will fail if database has different name
- **Impact**: Breaks migrations on different environments
- **Recommendation**: Remove `USE dayem_erp;` or make it configurable

**Issue #5: Employee Code Generation Race Condition (EmployeeModel.php:90-99)**
```php
$result = $this->query(
    "SELECT MAX(CAST(SUBSTRING(employee_code, 5) AS UNSIGNED)) as max_code FROM users WHERE employee_code IS NOT NULL"
)->fetch();
```
- **Problem**: Not atomic. Between SELECT and INSERT, another request could generate same code.
- **Impact**: Possible duplicate employee codes under concurrent requests
- **Recommendation**: Use database transaction or locking

**Issue #6: Employee Code Format Limitation**
- Format: `EMP-NNN` (3 digits per spec)
- `generateEmployeeCode()` uses `str_pad(..., 3, '0', STR_PAD_LEFT)`
- After EMP-999, next will be EMP-1000 (4 digits) which breaks the "NNN" format spec
- **Recommendation**: Update spec or handle overflow (e.g., EMP-1000 or increase padding)

## 4. Authentication & Security Review

**Issue #7: Status Not Re-validated After Login**

`Auth::isActive()` (Auth.php:45-48):
```php
public static function isActive(): bool
{
    return ($_SESSION['user_status'] ?? 'active') === 'active';
}
```
- **Problem**: Only checks SESSION value set at login time. If admin suspends/terminates an employee after they login, they retain access until session ends.
- **AuthMiddleware::validateSession()** (lines 75-93): Checks if session exists in DB but does NOT re-check user status from database.
- **Impact**: Suspended/terminated employees can continue using the system until they log out or session expires.
- **Recommendation**: Add status re-validation in `AuthMiddleware::validateSession()` by querying database.

**Finding #2: Login-Time Status Check ✅**
`AuthController::login()` (lines 124-134) correctly checks status at login time:
```php
if ($user['status'] !== 'active') {
    // Reject login with appropriate message
}
```
This meets FR-011 for new login attempts, but not for already-logged-in users.

**Issue #8: CSRF Token Handling Consistency** ✅
- Controller checks both JSON and POST data for CSRF token
- Uses `hash_equals()` for timing-safe comparison

**Issue #9: SQL Injection Protection** ✅
- Uses prepared statements via Model class
- No direct string concatenation in queries

**Issue #10: Password Handling** ✅
- Password hashed with `password_hash($password, PASSWORD_BCRYPT)`
- `must_change_password` flag set on creation
